# 查證流程（維護者用）

檢舉從 Issue 進來，查證後才寫進 `data/default-list.json`。每一則檢舉 Issue 都帶有
一份檢核清單，這份文件說明每一項要怎麼判斷。

## 一、先確認可查證

| 檢核 | 通過條件 |
| --- | --- |
| 粉專仍存在 | 網址可開啟，且確實是粉專／公眾人物專頁，不是個人帳號 |
| 頁面透明度 | 能看到建立日期、管理員所在地與人數、曾用名稱其中至少一項 |
| 佐證連結 | 連結可開啟，內容與檢舉描述相符 |
| 不是同名的其他粉專 | 用網址代號（不是名稱）確認身分 |

任一項做不到就標 `需要更多資料`，在 Issue 回覆說明缺什麼，不要直接收錄。

## 二、排除不收的情況

以下即使檢舉內容寫得很詳細，也一律退回並說明原因：

- 只是政治立場或支持對象不同
- 個人帳號（非公開粉專、非公眾人物專頁）
- 沒有可查證依據的猜測（「用語很像中國人」單獨不成立）
- 商業競爭、私人恩怨
- 同名就整批指認（「靠北 XX」「我是 OO 人」要逐一驗證）

## 三、決定等級

| 等級 | 條件 |
| --- | --- |
| `danger` 高風險 | 境外管理或中資背景**且**有具名的政治操弄記錄（研究單位、查核組織、司法或警方紀錄） |
| `warning` 需留意 | 有境外或不透明訊號，但沒有政治操弄的具名記錄 |
| `info` 提醒 | 同集團或同批經營，但內容非新聞輿論型 |
| `safe` 已澄清 | 名稱與被點名對象相似，但查證後確認無關。**這是保護性標記**，會顯示綠色提示而非警示 |

拿不定主意就往低一級標，或維持在 Issue 待查。寧可漏收，不要誤標。

## 四、寫進清單

在 `data/default-list.json` 的 `entries` 新增一筆：

```json
{
  "platform": "facebook",
  "handle": "粉專代號",
  "name": "粉專名稱",
  "level": "warning",
  "reason": "依據，寫清楚是誰在什麼時候查到什麼",
  "tags": ["分類標籤"]
}
```

- **優先用 `handle` 或 `profileId`**，比對才精確。查不到代號才退而用 `nameMatch`。
- `reason` 要能讓使用者自己重新查一次，不是只寫「有問題」。
- 有具名來源就寫進去（例如「DSET 具名」「無國界記者 2026/4」）。

改完跑一次測試，確認資料格式與同名情況都沒問題：

```bash
npm test
```

`test/default-list.test.js` 會檢查筆數統計、每筆都有依據、應排除的同名粉專不會誤警示。
新增項目時記得同步更新該檔的分級筆數期待值。

## 五、回覆與結案

- **收錄**：回覆等級與依據，附上 commit 連結，關閉 Issue。
- **退回**：說明是哪一項沒過（可查證性／排除情況／證據不足），關閉 Issue。
- **待查**：留著，標 `需要更多資料`。

## 六、申訴

申訴 Issue 的三種結果：

1. **移除** —— 原依據站不住腳。
2. **改標 `safe`** —— 名字相似但確認無關，之後逛到顯示綠色提示。
3. **維持並補充** —— 依據仍成立，把經營者的說法一併寫進 `reason`。

無論哪一種，都在 Issue 裡寫清楚理由。
